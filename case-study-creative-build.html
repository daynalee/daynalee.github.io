Creative Strategy

Building a Playable to Lift Advertiser Performance

When an advertiser's creative stops working, the usual answer is to wait on a production cycle. I stopped waiting. This is the process I use to build a working playable myself, from spec check through concept research to the small iteration decisions that decide whether it converts. Both playables below are mine and both run live in your browser.

Overview

Creative is usually the single biggest lever on an advertiser's performance and the slowest one to pull. A client partner spots the fatigue, writes the recommendation, and then everyone waits on a creative queue. By the time an asset arrives, the diagnosis is stale.

So I learned to build them. Not to replace a creative team, but to get a real, testable playable in front of an advertiser fast enough that the recommendation still matters. A working prototype also changes the conversation. It is much easier to get an advertiser to greenlight a direction they have already played than one they have seen on a slide.

Context

Problem Statement

Playables outperform static and video for most casual titles, but they are the hardest format to produce and the easiest to get rejected in ad moderation. Advertisers under-invest in them for exactly that reason. The blocker is rarely the idea. It is the distance between the idea and a file that actually passes spec and runs on a five year old Android phone.

My Role

I do the diagnosis, the concept research, and the build. Cleared brand assets and final approval come from the advertiser. Anything shipping to a live campaign goes through our creative and moderation teams. What I own is the first working version and the direction it proves.

The Build Process

1. Check every parameter before writing anything

Specs first, always. File size ceiling, single file packaging with every asset inlined, MRAID 3.0 handshake and close behavior, orientation support, the minimum OS the network still serves, click through handling, and the install call to action placement. Every one of these is a rejection reason, and every one is cheaper to satisfy at the start than to retrofit. A beautiful playable that is 400 kilobytes over the cap is a beautiful playable nobody sees.

2. Encode the specs as a reusable skill

I only wanted to learn the constraint list once. So I built the spec check, the packaging rules, and the compliance validation into a reusable build skill. Every playable now starts already compliant, and the interesting work starts at the concept instead of at the file format. This is the same instinct as the recommendation tracker on my demand growth account: if I do something more than twice, it becomes a process rather than a memory.

3. Research what is already winning

Before designing a mechanic I go look at what is running in the category and what is scaling. I am reading for three things: which interaction the category has trained players to expect, which hook shows up in the first two seconds of the top performers, and where there is a gap I can take. Playables in a category converge fast, so the useful question is usually not "what is best" but "what is everyone doing that I can do differently without confusing the player."

4. Generate assets that match the game's art style

This is where most quick-turn playables fall apart. An ad that does not look like the game it advertises creates a mismatch the player feels at install, and it shows up as bad post install retention rather than bad click through, so it is easy to miss. I sample the palette from the advertiser's own creative and build new assets against it, then hold every generated element to the game's actual art direction: line weight, corner radius, type treatment, lighting. The Flourish build below has its palette sampled directly from the client's own creative for exactly this reason.

5. Build, then iterate on the small things

The first working version is the starting point, not the deliverable. What I iterate on:

  • The mechanic itself: is the first tap obvious within one second, with no instruction read
  • Tap feedback: the glow, the particle, the scale bounce on touch. This is the difference between an ad that feels like a game and one that feels like a form
  • Audio: music bed and the confirmation sound on a successful action, with the whole thing still working silently, because most impressions are muted
  • Pacing to the end card: how fast the player reaches a win state and how the install call to action arrives, rewarding rather than interrupting
  • Failure states: what happens on a wrong tap. A playable that can be lost is a playable that gets abandoned
Build One

Flourish, Haunt the Plaza

A seasonal build for a garden design title. The mechanic is a single tap on a glowing plot that reveals a decorated transformation, which mirrors the game's actual core loop of placing and seeing the result. Palette sampled from the client's own creative so the ad reads as part of the game rather than as an ad about it. Packaged as one file under the size cap, MRAID 3.0, and written to render on an Android 4.4 and iOS 9 floor.

Build Two

Perfect365, four concepts in parallel

For a beauty title I built four different mechanics rather than one, because the useful question at the concept stage is which interaction the category responds to, and that is a test rather than an opinion. Each explores a different hook: a decision, a reveal, a matching task, and a personality quiz. Once the spec work is a skill, building four costs barely more than building one, and the advertiser gets a real choice instead of a single take it or leave it asset.

Challenges
  • The size cap fights the art: every asset is inlined into one file, so the quality of the art and the weight of the file are in direct tension. Most of the real engineering is compression decisions.
  • Old device floors: networks still serve very old operating systems. Modern conveniences like CSS custom properties are not safely available, so the code is written more plainly than it would be for the web.
  • Brand clearance is a real gate: a concept build can use placeholders, but nothing reaches a live campaign without cleared assets and advertiser sign off. Keeping that line clear is part of the job.
  • Honest limits: I am a client partner who builds, not a creative director. These are prototypes that prove a direction. Production polish and final asset work belong with the creative team.
Results
  • A working playable in days rather than a creative queue measured in weeks, so the recommendation lands while the diagnosis is still live
  • A reusable build skill that makes every subsequent playable compliant by default, so the effort goes into the concept instead of the packaging
  • Four parallel concepts for one advertiser, turning a creative opinion into a creative test
  • A tangible artifact for the conversation. Handing an advertiser something they can play is a fundamentally different ask than showing them a mock

The broader point is the one I keep landing on: the client partners who move accounts are the ones who shorten the distance between spotting a problem and putting something real in front of the client.
