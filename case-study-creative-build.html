Building a Playable to Lift Advertiser Performance

When an advertiser's creative fatigues, the fix usually sits in a production queue for weeks. I learned to build the playable myself so the recommendation still means something by the time it lands. Both builds below are mine, and both run right here in your browser.

The Problem

Creative is the biggest lever on advertiser performance and the slowest one to pull. A client partner spots the fatigue, writes it up, and then everyone waits on a creative queue. By the time the asset shows up, the diagnosis has gone stale.

Playables beat static and video for most casual titles, but they're the hardest format to produce and the easiest one to fail moderation on. What blocks you is getting from an idea to a file that passes spec and still runs on a five year old Android phone.

My role: the diagnosis, the concept research, and the first working build. Cleared assets and sign off come from the advertiser, and anything headed for a live campaign goes through our creative and moderation teams. I own the prototype and whatever direction it proves out.

The Build Process

1. Check every spec before writing anything

Size ceiling, single file packaging with every asset inlined, MRAID 3.0 handshake and close behavior, orientation, the oldest OS the network still serves, click through handling, install CTA placement. Every one of those is a rejection reason, and every one is cheaper to handle before you start than after.

2. Encode the specs as a reusable skill

I only wanted to learn that constraint list once, so the spec check, the packaging rules and the compliance validation all went into a reusable build skill. Now every playable starts out compliant and I get to spend the time on the concept instead of the file format. Same instinct behind the tracker on my UA account. If I do something more than twice, I'd rather turn it into a process.

3. Research what is already winning

Before I design a mechanic I go look at what's running in the category and what's actually scaling. I'm reading for the interaction players already expect and the hook the top performers open on. Categories converge fast, so the useful question is what everyone else is doing that I could do differently without confusing anyone.

4. Match the game's art style

This is where quick turn playables usually fall apart. If the ad doesn't look like the game, the player feels the mismatch at install, and that shows up as weak retention instead of weak CTR, so it's easy to miss entirely. I sample the palette straight from the advertiser's own creative, then hold every asset I generate to their art direction: line weight, corner radius, type treatment, lighting.

5. Build, then iterate on the small things

What I tune from there:

  • The mechanic: whether the first tap is obvious in under a second, without reading anything
  • Tap feedback: glow, particle, a little scale bounce, so it reads as a game instead of a form
  • Audio: a music bed and a confirmation sound, with everything still working on mute, since most impressions are silent anyway
  • Pacing: how fast the player gets to a win, and whether the install CTA feels like a reward or an interruption
  • Failure states: making sure a wrong tap can't end the run, because people quit a playable they can lose
Build One

Flourish, Haunt the Plaza

A seasonal build for a garden design title. One tap on a glowing plot reveals the decorated version, which mirrors the game's own place-and-see loop. I sampled the palette from the client's creative so the ad reads as part of the game rather than an ad about it. Single file, under the size cap, MRAID 3.0, written to render on an Android 4.4 and iOS 9 floor.

Build Two

Perfect365, four concepts in parallel

For a beauty title I built four mechanics instead of one. I wanted to know which interaction the category actually responds to, and you can't learn that from a single build. Each one opens on a different hook: a decision, a reveal, a matching task, a quiz. Once the spec work lives in a skill, four of them cost barely more than one, and the advertiser gets a real choice instead of a take it or leave it asset.

Challenges
  • Size cap versus art quality: every asset gets inlined into one file, so the art and the file weight are pulling against each other the whole time. Most of the real engineering ends up being compression decisions.
  • Old device floors: networks still serve very old operating systems, so conveniences like CSS custom properties are off the table and the code ends up plainer than anything I'd write for the web.
  • Clearance is a real gate: concepts can run on placeholders, but nothing reaches a live campaign without cleared assets and advertiser sign off.
  • Where I stop: I'm a client partner who builds, not a creative director. Production polish belongs with the creative team.
Results
  • A working playable in days, against a creative queue measured in weeks
  • A reusable build skill that makes every playable after it compliant by default
  • Four concepts in parallel for one advertiser, which turned a creative opinion into a creative test
  • Something the advertiser can actually play, and it's much easier to greenlight a direction you've already had your hands on
